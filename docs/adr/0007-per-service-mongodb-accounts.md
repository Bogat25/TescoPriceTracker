# 7. Per-service MongoDB accounts, with a visible fallback

**Status:** accepted, 2026-09-17

## Context

Every service connected to MongoDB as the same root user with the same
password. Any one of them - the public-facing API, a scraper, a one-shot job -
could read and write everything, including the alert users' data. A leak
anywhere was a leak everywhere, and rotating the credential meant rotating it
for everything at once.

## Decision

Three accounts by role, each with only the databases and rights it needs:

| Account | Used by | Rights |
|---|---|---|
| api | `api`, `recommendation-api` | read the catalogue, read/write the caches |
| scraper | `scheduler`, `auchan-scheduler`, `vectorizer` | write the catalogue and run state |
| alerts | `alert-service`, `alert-keycloak-sync` | read/write alerts and the user cache |

The passwords are generated by the SecretManager controller and never printed.
The accounts are created at startup by `mongo-users`, **from the application
image**, because Portainer does not ship repository files to the host and a
mounted init script would be an empty directory.

Until the accounts exist, a service falls back to the previous credentials and
**logs that it is doing so**.

## Consequences

- A compromised scraper cannot read the alert users' e-mail addresses.
- Credentials can be rotated one role at a time.
- The fallback keeps a deploy from becoming an outage when the secrets are not
  in place yet - but it is deliberately noisy, so "still on the shared
  credential" cannot quietly become the permanent state.
- The account creator is on the critical path at startup: when it could not
  start on 2026-09-17, every service waiting for it stayed down and the gateway
  answered 502. Running it from the application image is what fixed that, and
  is the reason it must never gain a dependency of its own.

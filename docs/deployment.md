# Deployment and operations

How a change reaches production, and what to do when something is wrong.

---

## 1. The pipeline

```
  git push origin master
        |
        v
  GitHub Actions (.github/workflows/ci.yml)
        |
        +-- quality      pytest + coverage, pip-audit, Angular tests + build,
        |                npm audit, compose model, Trivy (vuln, secret, config)
        +-- integration  the two-store tests against a real MongoDB
        |
        +-- build        four images, only after both jobs pass:
        |                  tescopricetracker          (api, schedulers, jobs)
        |                  tesco-tracker-frontend     (Angular + nginx)
        |                  tesco-tracker-embedding    (multilingual-e5-small)
        |                  tesco-tracker-keycloak     (realm baked in)
        v
  GHCR  ghcr.io/<owner>/<image>:master, :sha-<commit>, :latest
        |
        v
  Portainer git stack  (pulls this repository's docker-compose.yml)
        |
        v
  SecretManager controller  (Infisical -> stack environment -> redeploy)
```

A pull request runs the same tests and builds the images, but pushes nothing.

**The push is the release gate.** Nothing deploys on its own; the deploy step is
a deliberate action after CI is green.

---

## 2. Deploying

Through the SecretManager controller, which owns the stack environment:

1. `reconcile_deployments` — writes the current secrets and configuration into
   the Portainer stack environment.
2. `redeploy_deployment` — redeploys the stack.

**Only a redeploy re-pulls an image.** A reconcile alone updates the
environment and restarts with whatever image is already on the host, so a new
image tag needs both, in that order. This has cost a debugging session more than
once.

The stack must exist in the controller's `deployments.yaml` (both blocks) or it
is invisible to the controller, and reconcile silently does nothing for it.

### Configuration and secrets

Everything comes from Infisical through the controller; nothing is committed.
`.env.example` lists every variable with a safe default, and CI checks that the
compose model still resolves with it.

- A **configuration** value (`set_configuration_value`) is non-secret: a
  hostname, an image tag, a toggle.
- A **secret** (`generate_managed_secret`) is generated by the controller and
  never printed. The tracker's are the three MongoDB service passwords, the
  session signing secret, the Qdrant API key, the catalog token, the vector
  sync token and the Mongo Express password.
- To add one: declare it in `deployments.yaml`, reference it in
  `docker-compose.yml`, generate it, then reconcile **and** redeploy.

### A trap worth remembering

Portainer does not ship repository files to the host. A relative bind mount in
`docker-compose.yml` becomes an empty directory on the server, not your file.
Anything a container needs at startup — a Keycloak realm, an init script — must
be **baked into the image**. This is why `keycloak` and `mongo-users` are built
images rather than stock ones with a mount.

## 3. Health checks and rollback

Every service declares a health check against its **internal** address. The
public edge blocks non-browser agents, so a health check through the hostname
fails for reasons that have nothing to do with the service.

Portainer rolls the stack back when a deploy fails its health check. That
rollback can itself fail if a container cannot start at all — which is what
happened on 2026-09-17, when the MongoDB account creator ran from an image that
could not start and every service waiting for it stayed down. If both fail, the
stack is left partly up and needs a redeploy of the previous image tag.

**Rolling back:**
- *An image:* set the image tag variable back to the previous `sha-` tag,
  reconcile, redeploy.
- *A configuration change:* set the value back, reconcile, redeploy.
- *Everything:* revert the commit on `master`, let CI rebuild, redeploy. The
  data is untouched — no deploy migrates MongoDB.

## 4. After a deploy

```bash
python scripts/api_smoke.py                      # 19 checks, the neutral route
python scripts/api_smoke.py --route /api/tesco   # the legacy alias
```

Then look for what should *not* be there: no error events from `api`,
`alert-service`, `recommendation-api` or the schedulers in the Grafana error
views. Absence of errors is the signal; a dashboard that shows nothing new is
the good outcome.

[manual-test-plan.md](manual-test-plan.md) is the browser pass for anything the
smoke checks cannot see.

## 5. Runbooks

### The scrape did not finish

*Symptom:* no `scrape.published` for a store today, or `scrape.finalization_failed`.

The run state in `runs` / `auchan_runs` says which stage stopped and whether it
is `retryable`. A retryable day is resumed by the next scheduled pass on its
own — prices are already saved, only the publication is missing. If it is not
retryable, the shop changed its response shape: look for `AuchanContractError`
or the Tesco equivalent, fix the mapper, redeploy.

### Alerts were not delivered

*Symptom:* `scrape.finalization_failed`, price drops visible on the site but no
e-mail.

The alert service refused the trigger or was down. The next pass resends it.
Check `alert-service` health and its logs; if Keycloak was down, the user cache
sync (`alert-keycloak-sync`) may also be stale.

### Search is degraded

*Symptom:* responses come back with `"mode": "text"` although hybrid was asked
for, and `search.semantic_unavailable` appears in the logs.

The embedding service or Qdrant is unavailable. Search still answers from the
text index, so this is not an outage. Check `embedding-service` (it holds the
model in memory and unloads when idle) and `qdrant`.

### Vectors are stale

*Symptom:* new products are not found by meaning, only by name.

The vectorizer runs after each scrape and embeds only what changed. Check its
logs and `embedding_state`. A full re-index of ~38,000 products takes 4–8
minutes.

### MongoDB accounts are missing

*Symptom:* services fall back to the previous credentials, or cannot
authenticate at all.

The three passwords must exist in Infisical before the stack is reconciled.
`mongo-users` creates the accounts from the application image at startup; if it
cannot start, every service that waits for it stays down. Check that it exited
successfully, then redeploy.

### The category filter is empty

*Symptom:* `/api/prices/categories` returns nothing.

The mapping is rebuilt during the daily publish. Rebuild it by hand and read
the coverage it reports:

```bash
docker compose exec api python -m stores.admin categories
```

## 6. Running it locally

```bash
cp .env.example .env          # safe defaults; fill in what you need
docker compose up -d
```

First run: the database is empty, so the site has no products until a scrape
has run, and search has no vectors until the vectorizer has been. Keycloak
creates its realm on first start. To collect a little data without waiting for
the scheduler:

```bash
docker compose exec scheduler python -c "from scraper import scraper; scraper.run_scrape()"
docker compose exec auchan-scheduler python -c "from stores.auchan import crawler; crawler.run_crawl()"
```

Tests:

```bash
python -m pytest -q                      # unit tests; integration tests skip
MONGO_URI=mongodb://localhost:27017/ python -m pytest -q -m integration tests/integration
cd frontend && npm test -- --watch=false
```

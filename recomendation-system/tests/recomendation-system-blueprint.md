# Architectural Blueprint: E-Commerce AI Recommendation System

## 1. High-Level Overview
This system utilizes a "Worker Node" pattern to generate AI product embeddings on a powerful machine while serving recommendations locally from a lightweight edge device. It employs a hybrid-search algorithm (Semantic Vector Search + Business Rules) to deliver highly relevant, dynamically sorted product recommendations.

---

## 2. Hardware & Networking Infrastructure

*   **Production Server:** Raspberry Pi 5 (8GB RAM, ARM64)
    *   *Role:* Hosts the web APIs, primary database, and vector database.
*   **AI Worker Node:** Laptop 
    *   *Role:* Periodically polls the server for un-vectorized products, runs the heavy NLP models, and pushes vectors back to the server.
*   **Secure Networking:** Only accessed from admin_ingress (Private Mesh Network)
    *   *Role:* Creates a secure tunnel between the Laptop and the Pi. Prevents the Vector Sync API from being exposed to the public internet.

---

## 3. Database Architecture (On Raspberry Pi)

### Primary Data Store: MongoDB
*   **Purpose:** Stores full product JSON (prices, descriptions, categories) and user tracking/interaction history.
*   **Data Updates:** Continually updated by web scrapers (price changes, new items). 
*   **Flagging:** Uses a `needs_revector` boolean flag. Set to `true` when a scraper detects changes to a product's text fields (name, category, description). 
    This variable is true by default for all new products, ensuring they are picked up by the Laptop for vectorization.

### Vector Search Engine: Qdrant
*   **Purpose:** Stores mathematical representations (vectors) of products for sub-millisecond semantic similarity matching.
*   **Deployment:** Official Qdrant ARM64 Docker Container.
*   **Schema:** 
    *   `Vector`: The 384-dimensional array generated by the AI model.
    *   `Payload`: JSON metadata attached to the vector for strict filtering.
        *   *Format:* `{ "product_id" (or what the MongoDB uses): "100002595", "category": "Kulacsok és termoszok" }`

---

## 4. Microservices Architecture (On Raspberry Pi)

### Service A: Public API (Existing Backend)
*   **Accessibility:** Publicly exposed to the internet.
*   **Responsibilities:** 
    *   Serves the frontend application.
    *   Handles user authentication and sessions.
    *   **Calculation:** Handles the "in-memory" math (calculating the average user vectors based on liked items).
    *   **The Bridge:** Orchestrates queries between Qdrant (for semantic matches) and MongoDB (for user history and product hydration).
    *   **Sorting:** Applies business logic (sorting combined results by active discounts).

### Service B: Vector Sync API (Internal Microservice)
*   **Accessibility:** Bound strictly to the Tailscale IP/Docker network. Secured via an application-level API Token environment variable.
*   **Responsibilities:**
    *   **Vector Sync:** Provides endpoints for the Laptop to `GET` un-vectorized products and `POST` completed vectors.
    *   **Data Preparation:** Extracts the necessary text fields from the raw MongoDB JSON and formats the cohesive prompt string for the AI.
    *   **Data Ingestion:** Saves the incoming vectors and payloads into Qdrant, and updates the `needs_revector` flags in MongoDB.

---

## 5. The AI Model & Data Strategy (On Laptop & Service B)

*   **Model:** `intfloat/multilingual-e5-small` (via Hugging Face `sentence-transformers`). 
    *   *Why:* Industry standard for multilingual retrieval tasks. Extremely accurate for complex Hungarian grammar while outputting a lightweight 384-dimensional vector.
*   **Data Extraction (Prepared by Service B):**
    *   *Included Fields:* `name`, `brand_name`, `sub_brand`, nested department/aisle/shelf categories, `marketing`, and `other_information`.
    *   *Excluded Fields:* Dynamic data (prices), IDs, URLs, and generic legal notices.
*   **Prompt Construction:** The E5 model requires a strict prefix to understand its task.
    *   **The Final Prompt (Executed on Laptop):** `passage: [Concatenated String from Service B]`
    *   *Example String sent to Model:* `"passage: Tesco Home rozsdamentes acél termosz 1 literes. Márka: TESCO (TESCO) Home. Kategória: Otthon-hobbi, Otthon, Konyha és étkező, Kulacsok és termoszok. Jellemzők: Szigetelt. Szivárgásmentes. A meleget 5, a hideget 9 órán keresztül tartja. Anyagösszetétel: rozsdamentes acél, polipropilén."`

## 6. Data Flows & Execution Pipelines

### Pipeline A: The Vector Generation Loop (Background)
1.  **Pull:** Laptop pings Service B via Tailscale: *"Give me 100 products where vector is null OR needs_revector is true."*
2.  **Format:** Service B returns the array of products, pre-formatting the data into the clean, concatenated text strings.
3.  **Process:** Laptop prepends `"passage: "` to each string and generates the 384-dimensional vectors using the Python script.
4.  **Push:** Laptop sends a payload back to Service B: `[ { mongo_id, category, vector } ]`.
5.  **Store:** Service B saves the vector and payload into Qdrant, and updates MongoDB setting `needs_revector: false`.

### Pipeline B: The Recommendation Engine (User Facing)

**Scenario 1: The "Cold Start" (User is not logged in / no history)**
1.  Frontend requests recommendations from Service A.
2.  Service A recognizes a null user profile.
3.  Service A bypasses Qdrant entirely.
4.  Service A queries MongoDB for the top globally discounted items: `db.products.find({ "price_history.discount": { $ne: null } }).limit(10)`.
5.  Service A returns results to the frontend.

**Scenario 2: The Logged-In User**
1.  **Fetch History:** Service A pulls the user's alert tracked items from MongoDB.
2.  **Group by Deepest Category:** Service A groups items by their `shelf_name` (e.g., all tracked thermoses in one group, all tracked TVs in another). The top 1 to 5 groups are selected. (use the latest tops)
3.  **Calculate Mean Vectors:** For each category group, Service A calculates the average vector of those specific items.
4.  **Parallel Qdrant Search:** Service A fires concurrent queries to Qdrant for each mean vector.
    *   *Crucial Step:* Applies a strict **Payload Filter** ensuring Qdrant only searches within that specific category (preventing "Vector Bleed").
    *   *Over-fetching:* Requests the top 50 matches per category.
5.  **Merge & Hydrate:** The returned Qdrant `mongo_id` arrays are flattened and deduplicated. Service A queries MongoDB to fetch the full product details for these IDs.
6.  **Apply Business Logic (Hybrid Search):** Service A sorts the hydrated array in memory, pushing any items with active discounts to the top of the list.
7.  **Return:** The final, curated array is sent directly back to the frontend by Service A.

**Frontend**
Update the frontend that on the search page, before the user starts searching, it calls the recommendation API to get the recommended products. The frontend should be able to handle both the "cold start" and logged-in user scenarios seamlessly, displaying the most relevant products based on the user's interaction history and current promotions.
